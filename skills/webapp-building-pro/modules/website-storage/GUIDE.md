# 使用条件

此模块实现 Kimi 平台对象存储，需服务端和真实网关资源；普通本地环境没有这些凭证时不要调用，也不自动建议发布网站来申请资源。检查配置时只输出键是否存在，不输出值；费用与限额以当前平台契约为准。包中 SDK 文件在本模块的 `templates/storage.ts`，实际复制时使用其绝对路径。

# Website Storage (Object Storage)

**Stack**: platform-managed object storage (TOS) reached through the platform gateway. The site never holds cloud credentials — the platform injects them.

**Prerequisite**: `backend-building`. The SDK is **server-only**: the credential must never reach the browser, so every file operation goes through the project's own backend (tRPC + Hono).

## Platform-injected environment (never ask the user, never hardcode)

| env | meaning |
|---|---|
| `KIMI_AGENTGW_API_KEY` | per-owner gateway credential — **server-side only** |
| `KIMI_AGENTGW_BASE_URL` | gateway entry of the current environment |
| `KIMI_STORAGE_RESOURCE_ID` | this site's storage resource id (not a secret) |

The platform injects all three **into the project's `.env`** (sandbox and published runtime). The running site sees them because the server loads that file (`api/lib/env.ts` → `import "dotenv/config"`) — but **a one-off script you run yourself does not load `.env` automatically**:

- `npx tsx storage-check.ts` therefore sees an empty environment and the SDK throws `STORAGE_NOT_PROVISIONED`. That is **not** proof that provisioning is missing. Load the file first:

```bash
npx tsx -r dotenv/config storage-check.ts     # or put `import "dotenv/config";` as the first line
```

- Diagnose in this order before saying anything to the user: ① does `.env` contain the keys (`grep -c '^KIMI_' .env`)? ② if yes → it was a loading problem, fix the script; ③ if `.env` has no `KIMI_` entries → the site is genuinely unprovisioned: 在已确认的 Kimi 平台按真实资源状态处理；普通本地开发需配置适用的存储服务，不自动发布. Do **not** conclude "the sandbox has no credentials" from a script failure alone.
- Never invent a fallback: no `localStorage`, no files in the repo, no DB rows, and no "store an external image URL as the key and render it directly" (see Rules below).

## Workflow

1. **Initialize the project** — `webapp-building` first, then graft `backend-building` (step 1 below).
2. **Move the SDK into the project's own lib** (step 2 below) — `api/lib/storage.ts`.
3. **Wire the site** — a tRPC router for upload/list/delete, and `getPresignedUrl` for rendering (step 3 below).

## 1. Initialize the project (backend building)

Storage needs a server, so the project must be a full-stack one. If it is not initialized yet:

```bash
# frontend
bash ../../scripts/init-webapp.sh "My App"
cd /mnt/agents/output/app

# backend graft (db / auth are independent of storage — pick what the site needs)
bash ../backend-building/scripts/init.sh "My App" --features db
```

Verify the graft before continuing: `npm run check` must pass. Storage itself needs **no** extra feature flag, no database table and no migration.

## 2. Move the SDK into the project's lib

```bash
cp ./templates/storage.ts api/lib/storage.ts
```

Rules:

- Keep it under **`api/`** (server code). `tsconfig.server.json` already includes `api/`, so no config change is needed.
- **Never** copy it into `src/` (frontend): the API key would end up in the browser bundle.
- Do not edit the file and do not duplicate it. To upgrade, overwrite it with this template again.

## 3. Use it — methods and wiring

### Methods

| Method | Purpose | Notes |
|---|---|---|
| `uploadFile({ fileContent, fileName, contentType? })` | Upload bytes (server-side) | Returns `{ key, fileName, size, contentType, etag, reviewStatus }`. Key is generated by the SDK (8-char suffix before the extension); same key overwrites silently |
| `getPresignedUrl({ key, download? })` | Url for the browser to render/download | Facade URL, valid ~10 min, redirects to storage. Never persist it |
| `getPresignedUrls({ keys, download? })` | Batch version | Returns `{ urls, failures }` — partial failure does not fail the batch |
| `readFile({ fileKey })` | Read bytes server-side | Returns `Uint8Array` (Node: `Buffer.from(bytes)` if you need `Buffer`) |
| `headFile({ fileKey })` | Metadata (`size`, `contentType`, `etag`, `lastModified`) | |
| `fileExists({ fileKey })` | Boolean existence check | |
| `listFiles({ prefix?, delimiter?, maxKeys?, pageToken? })` | List | `delimiter: "/"` → one level (`folders` + `objects`); `delimiter: ""` → flat recursive; page with `nextPageToken` |
| `deleteFile({ fileKey })` / `deleteFiles({ fileKeys })` | Delete | Idempotent: deleting a missing key still reports success. **Call it only from an owner-checked / authenticated path** — never expose it on `publicQuery` |

`storage` is a lazy singleton: `import { storage } from "../lib/storage"` — it reads the environment on first call, so the module can be imported even before storage is provisioned.

### Backend wiring (tRPC router)

**Pick the procedure type per endpoint — do NOT put upload/delete on `publicQuery` unless anonymous access is really the product requirement.**

- Site has the **`auth` feature** → `api/middleware.ts` also exports `authedQuery` (and `adminQuery`). Put `upload` / `remove` / per-user `list` on `authedQuery`, record the owner, and check ownership before deleting.
- Site is **`db`-only** → only `publicQuery` exists. A public `upload` is acceptable only for a deliberate anonymous drop-box (public feedback form), and then keep a size cap and never expose `remove`. With no auth there is no ownership model, so **don't expose delete at all**.

Why it matters: `upload` on a public procedure lets any anonymous visitor fill the site's storage quota (the owner pays), and `remove` on a public procedure takes an arbitrary `key` and deletes whatever another visitor uploaded.

```ts
// api/storage-router.ts — site WITH the auth feature
import { z } from "zod";
import { TRPCError } from "@trpc/server";
import { eq } from "drizzle-orm";
import { createRouter, authedQuery } from "./middleware";
import { storage } from "./lib/storage";
import { getDb } from "./queries/connection";
import { files } from "../db/schema";   // your own table, e.g. files(key, ownerId, name, size)

export const storageRouter = createRouter({
  // The browser posts a file to this mutation; the server uploads to storage.
  upload: authedQuery
    .input(z.object({
      name: z.string().min(1).max(200).refine(v => !/[\\/]/.test(v) && !v.includes("..")),
      contentBase64: z.string().max(7_000_000), // example: cap decoded uploads to 5 MB too
      contentType: z.string().optional(),
    }))
    .mutation(async ({ ctx, input }) => {
      const bytes = Uint8Array.from(Buffer.from(input.contentBase64, "base64"));
      if (bytes.byteLength > 5 * 1024 * 1024) throw new TRPCError({ code: "PAYLOAD_TOO_LARGE" });
      const saved = await storage.uploadFile({
        fileContent: bytes,
        fileName: `u/${ctx.user.id}/${input.name}`, // reject separators in the user-supplied name
        contentType: input.contentType,
      });
      // Persist the key AND the owner — the ownership check below needs it. Never persist the URL.
      await getDb().insert(files).values({ key: saved.key, ownerId: ctx.user.id, name: saved.fileName, size: saved.size });
      return { key: saved.key, size: saved.size, etag: saved.etag };
    }),

  // Render: hand the browser a short-lived URL derived from the stored key.
  url: authedQuery
    .input(z.object({ key: z.string() }))
    .query(async ({ ctx, input }) => {
      const row = await getDb().query.files.findFirst({ where: eq(files.key, input.key) });
      if (!row || row.ownerId !== ctx.user.id) throw new TRPCError({ code: "FORBIDDEN" });
      return { url: (await storage.getPresignedUrl({ key: input.key })).url };
    }),

  // Scope listing to the caller's own prefix / owner column.
  list: authedQuery
    .input(z.object({ prefix: z.string().optional() }))
    .query(async ({ ctx, input }) =>
      storage.listFiles({ prefix: `u/${ctx.user.id}/`, delimiter: "" })),

  // Owner-checked delete: look the key up, compare the owner, then delete.
  remove: authedQuery
    .input(z.object({ key: z.string() }))
    .mutation(async ({ ctx, input }) => {
      const row = await getDb().query.files.findFirst({ where: eq(files.key, input.key) });
      if (!row || row.ownerId !== ctx.user.id) throw new TRPCError({ code: "FORBIDDEN" });
      await storage.deleteFile({ fileKey: input.key });
      await getDb().delete(files).where(eq(files.key, input.key));
      return { ok: true };
    }),
});
```

`db`-only site (no `auth`): `import { createRouter, publicQuery } from "./middleware"` and use `publicQuery` for every endpoint — for uploads that are intentionally anonymous, cap the input size and **omit `remove` entirely** (it cannot be made safe without an owner).

Register the router in `api/router.ts` (`storage: storageRouter`), then run `npm run check`.

### Rules that matter

- **Persist keys, never URLs.** URLs expire (~10 min) — store the key and mint a URL at render time.
- **Files go through your own backend**, not straight from the browser to the gateway.
- One file ≤ **100 MB** (server-enforced; larger fails with `STORAGE_FILE_TOO_LARGE`).
- Content is reviewed synchronously on upload: images return fast; documents (pdf/office/zip/txt/md/csv/rtf) can take **~10 s**, so client timeouts must be generous. Rejected content fails the upload with `STORAGE_REVIEW_REJECTED` — the object is never stored.
- `fileName` may contain folders and non-ASCII characters (中文/空格 are valid); it must be ≤ 512 bytes, must not start with `/`, and must not contain `//`, `\`, `..` or control characters.
- **Keys are unique per upload by design** (suffix); reuse a key only when you intend to overwrite.
- **`upload` is an authenticated, quota-consuming operation.** Anonymous upload is a product decision, not a default; delete always needs an ownership check (see Backend wiring).
- **Never persist an external URL as a key** (e.g. seeding with `https://images.unsplash.com/...` and rendering any key that starts with `http` directly). It breaks the key-only model and quietly ships a site that bypasses platform storage. If storage is genuinely not provisioned, report that instead of changing the data model.
- `KIMI_AGENTGW_BASE_URL` is an **absolute URL** injected by the platform (dev `https://agent-gw-dev.dev.kimi.team/coding/v1`, prod `https://agent-gw.kimi.com/coding/v1`). Never rewrite it; if a site reports `STORAGE_NOT_PROVISIONED` with a base-URL message, the injected value is malformed — tell the user instead of hardcoding one.

### Errors

All failures are `StorageError` with a stable `code` (and `retryable`):

`STORAGE_NOT_PROVISIONED` · `STORAGE_FORBIDDEN` · `STORAGE_RESOURCE_FROZEN` · `STORAGE_QUOTA_EXCEEDED` · `STORAGE_FILE_TOO_LARGE` · `STORAGE_INVALID_INPUT` · `STORAGE_REVIEW_REJECTED` · `STORAGE_OBJECT_NOT_FOUND` · `STORAGE_RATE_LIMITED` · `STORAGE_UPSTREAM_ERROR`

The gateway returns `{"error": {"code": "STORAGE_*", "message": "..."}}` — there is no diagnostic/request id field, so quote `code` + `message` when reporting an issue upstream.

`STORAGE_NOT_PROVISIONED` has two distinct causes: the script/runtime did not load `.env` (most common when you run a standalone check), or the site really has not been provisioned yet. Distinguish them by inspecting `.env` before you tell the user anything.

Surface the code to the user in plain language (e.g. quota → suggest cleaning up old files), and only retry `retryable` errors. A malformed injected base URL surfaces as **non-retryable** `STORAGE_NOT_PROVISIONED`, not as `STORAGE_UPSTREAM_ERROR`.

## Verification (do this before telling the user it works)

0. If you verify from a script rather than the running site, load the project env first (`npx tsx -r dotenv/config …`); confirm `.env` actually has the keys (`grep -c '^KIMI_' .env`). A bare `npx tsx` sees no `KIMI_*` and falsely reports `STORAGE_NOT_PROVISIONED`.
1. `npm run check` passes (the SDK compiles under the project's server tsconfig).
2. Upload through the site's own flow, then confirm with **two independent reads**: `fileExists({ fileKey })` / `headFile({ fileKey })`, and the file listed by `listFiles({ prefix })`.
3. Open the `getPresignedUrl` result in the browser and confirm the content matches what was uploaded.
4. Delete and re-check `fileExists` → `false`.

Never report "storage works" from a successful upload response alone, and never claim a preview URL is permanent.

## Billing — never tell the user the site is free

Storage, the published site's runtime and the APIs it calls all consume the owner's quota. When the user asks about cost, or when you turn on something that actually consumes quota (enabling storage, publishing, cloud/API calls), say it plainly in the conversation:

> 网站将根据使用的云服务和 API 调用产生计费。

- Never answer 「不按次收费 / 不会扣额度 / 访问者完全免费」: publishing bills the owner **daily** for server cost, and stored bytes count against the owner's **10GB** per-user quota.
- Never invent amounts or promises. Describe the mechanism (quota + daily server cost for a published site) and point the user to 设置 → 额度和发票 → 使用明细 for the real entries.
- Quota exhaustion is a hard stop: uploads fail with a quota error once the resource quota is used up — tell the user before that happens rather than after.
