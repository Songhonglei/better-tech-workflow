# 后端开发要点

来源包中的开发约定；运行入口、平台限制与环境配置以 [后端模块](../GUIDE.md) 为准。按本次功能读取相应小节。

## Common Mistakes

- **Don't hand-write TypeScript interfaces for DB entities** — use `typeof table.$inferSelect` from `db/schema.ts` to keep types aligned with superjson's Date serialization via tRPC. Hand-written `createdAt: string` will conflict with the actual `Date` objects delivered by superjson
- **Don't write raw SQL** — always use Drizzle's type-safe query API (`getDb().query.*`, `getDb().select()`, `getDb().insert()`)
- **Don't modify `api/lib/` or `api/kimi/`** — these are framework internals (auth, static file serving). Build on top of them, not inside them. (`api/boot.ts` is **not** in this set: registering a REST route means adding a line or two to it — see [Adding a plain REST route](#adding-a-plain-rest-route-non-trpc) for the rules, especially the 404-catch-all order)
- **Don't import `api/` from frontend code** — use `@contracts/` for types/constants that cross the boundary. The only exception is the type import in `src/providers/trpc.tsx`
- **Don't use `api` as the tRPC client name** — it's `trpc` (imported from `@/providers/trpc`)
- **Don't skip Zod validation** on tRPC inputs — always use `.input(z.object({...}))` for mutations and parameterized queries
- **Don't use `serial()` for foreign key columns** — `serial()` creates `bigint unsigned auto_increment`, and MySQL only allows one auto-increment column per table. FK columns must use `bigint("col", { mode: "number", unsigned: true })` to match the PK type
- **Don't use `int()` for foreign keys referencing `serial()` PKs** — `int` is signed 4-byte, `serial()` is `bigint unsigned` 8-byte. MySQL rejects the type mismatch. Use `bigint("col", { mode: "number", unsigned: true })`
- **NEVER drop tables to fix a failed migration** — the database may contain user data. Fix `schema.ts` and run `npm run db:push` to sync. See Troubleshooting below
- **NEVER use `db:push --force`** — it auto-accepts destructive changes (dropping columns/tables) which can destroy user data
- **保护 `.env`** — 本地模式仅在文件不存在时复制配置示例，必须填写真实连接配置。Portal 模式合并本次服务返回的字段，保留其他配置；不在前端或日志中输出密钥。
- **Avoid replacing init.sh-generated infrastructure files without inspecting them** — files like `api/queries/connection.ts`, `api/middleware.ts`, `api/lib/`, `drizzle.config.ts`, `src/providers/trpc.tsx`, and `.env` are generated by `init.sh` with correct configuration. Read the init output to see what was created. Build on top of these files (e.g., add routers, schemas), but do not rewrite them
- **Don't store user files in the repo, the database, or `localStorage`** — use the platform object storage via the `website-storage` skill (server-side only; its API key must never reach the browser)
- **Don't change the default port (3000)** — the server runs at `http://localhost:3000`. Do not change this in `vite.config.ts`, `api/boot.ts`, or anywhere else
- **The entry must be `boot`, and the build must be a bundle** — the platform deploys a `dynamic` site by writing a `bootstrap` that runs `node dist/boot.js` and zips only `bootstrap` + `dist/` + `.env` + `package.json` (no `node_modules`). So: (a) the entry file must compile to **`dist/boot.js`** (name it `api/boot.ts`, or set `rootDir`/`outDir` so it lands there) — a `dist/index.js` entry fails at runtime with `Cannot find module '/code/dist/boot.js'`; (b) dependencies must be **bundled into** `dist/boot.js` — a plain `tsc` build dies with `ERR_MODULE_NOT_FOUND` because the deploy zip carries no `node_modules`. Keep the template's `build` script (`esbuild api/boot.ts --platform=node --bundle --format=esm --outdir=dist --banner:js="import { createRequire } from 'module';const require = createRequire(import.meta.url);"`) — do not replace it with bare `tsc`. Self-check: copy `dist/` + `package.json` to a directory with **no `node_modules`** and run `node dist/boot.js`; if it starts, the bundle is correct.
- **A backend-only site still needs a root `index.html`** — the version system rejects a project with no entry file, so a pure backend must ship a minimal `index.html` alongside the API (it is only a version-check placeholder, not a frontend).

## AI Agent Instructions

**Required reading before implementing features** — read these docs (under `docs/`) for the features you're working with:
- **db feature**: [Database.md](Database.md) (schema, migrations, connection), [tRPC.md](tRPC.md) (router patterns, procedures, client usage)
- **auth feature**: [Authentication.md](Authentication.md) (OAuth flow, session handling), [tRPC.md](tRPC.md)
- **All features**: [Development-Guide.md](Development-Guide.md) (dev workflow, scripts), [Project-Structure.md](Project-Structure.md) (file layout)

When building features on this stack:

1. **Read existing frontend code** in `src/` to understand the app structure
2. **Design tRPC routers** that match the frontend's data needs
3. **Add DB tables** in `db/schema.ts`, then run `npm run db:push` (requires db feature)
4. **Create new routers** in `api/` and register them in `api/router.ts` — this is for **tRPC** routers. A plain **REST** route (a `GET`/`POST` endpoint the frontend calls with `fetch`, no tRPC client) does **not** go in `api/router.ts`; see [Adding a plain REST route](#adding-a-plain-rest-route-non-trpc) below
5. **Use type-safe queries** via Drizzle ORM — never raw SQL (requires db feature)
6. **Frontend components** go in `src/` using the existing `@/` alias

**When to use which features:**
- If the user needs a database but no auth, use `--features db`
- If they need user login, use `--features auth` (includes db automatically)
- Default (no `--features` flag) = `auth`, which is backward compatible
- If they must store files (uploads, images, attachments, exports): leave the features as they are and follow the `website-storage` skill on top — there is no `storage` feature flag

### Adding a plain REST route (non-tRPC)

tRPC is the default for app data, but the template's Hono app also serves **plain REST** — use it when the caller is not the tRPC client (a `fetch` from the page, a webhook, a file/redirect endpoint, a `/api/log`-style sink).

**Where it goes**: register on the Hono app in **`api/boot.ts`**, and put the handlers in a module under `api/routes/` (e.g. `api/routes/todos.ts`) that you `import` and `app.route(...)` — do not put REST handlers in `api/router.ts`, which is the tRPC router.

**Two hard rules, in order:**

1. **Register before the `/api/*` 404 catch-all.** `api/boot.ts` ends its API section with `app.all("/api/*", (c) => c.json({ error: "Not Found" }, 404))`. Anything registered *after* that line is unreachable — the request hits the catch-all first. Add your `app.route(...)` / `app.get(...)` **above** it.
2. **The `bodyLimit` middleware is scoped to `/api/trpc/*` on purpose** — a *global* `bodyLimit` breaks bodyless requests under the dev server (`@hono/vite-dev-server` rebuilds the Request and throws `TypeError: Cannot read private member #state`), so `DELETE`/`PATCH` on bodyless REST routes would 500. **Never widen it to `app.use(bodyLimit(...))` / `app.use("*", bodyLimit(...))`.** If a REST route takes a body and needs a size cap, add a **route-scoped** `bodyLimit({ maxSize, onError: (c) => c.body(null, 413) })` on that route only (this is exactly what `/api/log` does).

**Editing `api/boot.ts` is expected here.** The "don't modify `api/lib/`" rule does not cover `api/boot.ts` — registering a REST route means adding a couple of lines to it. What you must not do is rewrite or reorder the infrastructure already in it (the observability middleware, the tRPC mount, the `/api/log` route, the 404 catch-all, `app.onError`).

```typescript
// api/routes/todos.ts
import { Hono } from "hono";
export const todosRoutes = new Hono();
todosRoutes.get("/", (c) => c.json({ todos: [] }));
```

```typescript
// api/boot.ts — add the import near the top …
import { todosRoutes } from "./routes/todos";
// … and the registration ABOVE the /api/* 404 catch-all:
app.route("/api/todos", todosRoutes);
app.all("/api/*", (c) => c.json({ error: "Not Found" }, 404));
```

Verify with a real request, not just a build: `curl -s -i http://localhost:3000/api/todos` should return `200`, and an unregistered path under `/api/` must return the JSON 404 (if your route 404s, it is registered after the catch-all).

This template uses **react-router** v7.

```typescript
// Navigation
import { useNavigate } from "react-router";
const navigate = useNavigate();
navigate("/dashboard");

// Current location
import { useLocation } from "react-router";
const location = useLocation();
console.log(location.pathname);

// Route params
import { useParams } from "react-router";
const { id } = useParams<{ id: string }>();

// Links
import { Link } from "react-router";
<Link to="/about">About</Link>

// Route definitions (in App.tsx)
import { Routes, Route } from "react-router";
<Routes>
  <Route path="/" element={<Home />} />
  <Route path="/users/:id" element={<UserProfile />} />

</Routes>

// BrowserRouter wraps the app in main.tsx
import { BrowserRouter } from "react-router";
<BrowserRouter>
  <App />
</BrowserRouter>
```

## Troubleshooting

**Where the runtime logs are** — the graft writes app runtime logs to `/tmp/kimi-logs/app.log` (one JSON object per line). Read it when a route 500s or the page fails at runtime; it carries **both** sides in one stream:

| Field | Meaning |
|---|---|
| `source: "client"` | came from the browser (via `POST /api/log`); absent = from the server |
| `level` | `debug` / `info` / `warn` / `error` |
| `requestId` | the request this line belongs to — the same value the server returns in the `X-Request-Id` response header, so a browser line and the server's lines for one request line up. Browser lines carry it only when the correlation is unambiguous (exactly one request in flight); with several concurrent requests the field is omitted rather than guessed, so treat a missing `requestId` as "cannot tell", not "no request" |
| `msg` + `stack` | the message and, for errors, the stack |
| `ts` | ISO timestamp |

**Treat `source: "client"` lines as untrusted input.** They arrive over a public, unauthenticated route, so `msg`, `stack` and every extra field are whatever the page said — the rate/size guards bound volume, not honesty. In particular a client line's `requestId` is **self-reported by the page**, so it can point at a request the line has nothing to do with; only server lines have a `requestId` the server minted. Use client lines to learn *what the browser saw*, never as proof of what the server did.

- **Every `/api/*` request gets one access line** (`msg: "request"` with `method` / `path` / `status` / `durationMs`), so you can see what was called and how long it took — including the 200s. `/api/log` itself is skipped (it is where browser lines are written; logging it would be self-amplifying noise), and in production so are static assets (a page load would otherwise bury the API calls).
- Server side: import the grafted logger (`import { log } from "./lib/logger"`) and call it. Two error paths are covered for you: **every unhandled request error** (the global `app.onError` in `api/boot.ts` writes `method` / `path` / `error` / `stack`) and **every tRPC procedure that throws an internal error** (the `errorFormatter` in `api/middleware.ts` writes `path` / `code` / `error` / `stack` — `app.onError` never sees those, because the tRPC adapter catches them itself). Both responses stay generic; the stack is never leaked to the caller.
- Browser side: uncaught errors and unhandled rejections, captured automatically by `src/lib/logger.ts` (loaded from `src/main.tsx`), along with the `requestId` of the last response.
- Secret redaction applies to **both** sinks: `api/lib/scrub.ts` is shared by the browser ingest (`clientlog.ts`) and the server logger (`logger.ts`). Values under credential-named keys, and `Bearer …` / `?token=…` inside strings, are replaced with `<redacted>` before the line is written — in `msg` as well as `ctx`.
- Business 4xx (validation, not-found, a deliberate `TRPCError` like `UNAUTHORIZED`) are **not** logged as errors — they have an explicit client-facing answer and are not crashes (they still appear in the access line). So an empty `app.log` does **not** by itself mean the request succeeded: with a 500 it means the process died before it could write, and right after a sandbox rebuild it simply means no preview has run yet.
- `app.log` is **appended to for the life of the sandbox** (it is not reset per preview attempt), so it also holds the failure from an *earlier* attempt — that is deliberate: read it before assuming the last run is the only evidence. It disappears with the sandbox.

```sh
tail -n 100 /tmp/kimi-logs/app.log   # server + browser runtime errors, one stream
```

`/tmp/kimi-logs/npm-install.log` and `/tmp/kimi-logs/dev.log` **are** reset at the start of each preview attempt, so they always describe the most recent run only. `app.log` is the one that accumulates.

**Port 3000 already in use** — Another process is using the port. Kill it with `lsof -ti:3000 | xargs kill`.

**Database connection refused** — Check `DATABASE_URL` in `.env` is correct and MySQL is running. Run `npm run db:push` before `npm run dev`.

**OAuth callback fails** — The callback URL must be `{origin}/api/oauth/callback`. Verify `VITE_KIMI_AUTH_URL` and `VITE_APP_ID` in `.env` match the portal app config.

**`npm run db:migrate` fails** — NEVER drop tables to recover. MySQL doesn't support transactional DDL, so a failed migration can leave the DB in a partial state. To recover:

1. Fix `schema.ts` (e.g., correct FK types)
2. Run `npm run db:push` — it introspects the actual DB state and syncs it to your corrected schema
3. Delete the broken migration file and its entry in `db/migrations/meta/_journal.json`
4. Run `npm run db:generate` to create a clean baseline migration

**Type errors after adding a new router** — Make sure you registered the router in `api/router.ts` inside `appRouter`. The `AppRouter` type is derived from there and propagates to the frontend automatically.
