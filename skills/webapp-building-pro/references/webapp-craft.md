# Craft knowledge

## Principles (values for every deliverable)

1. **Reuse ladder**: built-in capabilities → official examples/templates → maintained free solutions → user's existing assets → build your own. Building your own is always the last resort; hand-writing code for functionality an existing package already provides is a violation.
2. **Research protocol**: for non-trivial tasks, consult relevant official documentation or maintained examples when the task warrants it. Stop immediately and go back to research when any of these signals appears: trial-and-error parameter tuning one by one, writing code for existing functionality, asking the user to "just try it", the same approach failing for the third time.
3. **Evidence-driven**: "it compiles / it opens" ≠ done. Every promised feature must actually be triggered once in the real runtime environment with evidence left behind (screenshot / console / read-back value); do one cold-start verification before delivery. Verify the presentation layer together with the logic layer — if the data is right but the visuals are wrong, users will still judge it as not done.
4. **render → look with your own eyes → attribute to a variable → fix → re-render**: the verification loop is the source of quality. Every defect must be attributed to a concrete variable before fixing; escalate level by level: patch → retune → change representation → re-plan. Never pile patches onto a broken structure, never blindly retry changes. **Falsely reporting a check that never happened is the most serious failure.**
5. **Honest delivery**: the report states what was reused and its source, what was simplified, what was assumed, and what was not completed; record licenses for third-party assets (CC0 = use freely / CC-BY = attribution / NC-ND = do not ship), and maintain `CREDITS.md` when needed.

## Universal workflow

1. **Lock the plan**: one sentence to lock the aesthetic direction + bound the scope (must-ship list — rather cut than bloat) + budget (performance/entity/size budgets for the busiest view). Only inside Kimi, when Musepool is configured and its use is authorized, retrieval comes *before* this lock — see "Website design / web apps — craft rules".
2. **Environment check (proportionate to task risk)**: is the toolchain present, are the versions right, are the channels working (use an isolated probe when writes are authorized; a read-only check otherwise); fix problems first — never start work on a broken environment.
3. **Vertical slice**: first get the core loop working end to end (the page opens and its primary flow works), and protect it from being broken by later work.
4. **Deepen**: add content and depth per the plan; rather cut features than bloat — never stop at "broad but shallow".
5. **Verify**: test in a real browser + look at the screenshots yourself + fix + re-verify (see "Verification" below).
6. **Deliver**: deliver exactly the agreed artifacts, keep user-requested evidence and working notes; clean only disposable files created for this task.

## Website design / web apps — craft rules

- **参考先行**：用户已有设计或选定模板时优先沿用。仅在 Kimi 环境、需要设计参考且 Musepool 网关与费用范围已确认时，读 `../modules/musepool/GUIDE.md`，默认一次 recall 加一次 fetch；其他环境提示一次“Musepool 仅在已配置的 Kimi 环境使用，本次继续使用已有素材或其他参考”，不尝试安装或调用 Musepool，不让它阻塞开发。
- **Lock the aesthetic direction first**: define it with 3–5 concrete decisions (font pairing + color stance + layout stance + motion + 1 signature detail), commit to it throughout — nothing half-baked; re-derive it from context every time, and beware of "second-order defaults". When musepool ran, these 3–5 decisions are the record of what you took from the references, not a fresh invention.
- **Anti-slop bans**: Inter/Roboto/system default fonts, purple-blue gradients (especially gradient text), emoji as icons (use an SVG icon library), centered symmetric template layouts, uncustomized component-library default themes, cream/beige backgrounds, an eyebrow kicker and 01/02 numbering scaffolding on every section, side color bars >1px, nested cards.
- **Precedence when musepool ran** (settled — do not improvise a resolution). Every rule in this section falls into exactly one of the buckets below; if you cannot place a rule, it is a taste rule.
  - **Engineering floors never relax for a reference.** Contrast (body ≥4.5:1, large text/UI ≥3:1, dark mode checked separately), a visible `:focus-visible`, hover/focus/active/disabled states, keyboard operability of hidden/dynamic UI, the mobile rules R0–R6 and interaction integrity I0–I5 (no dead controls) *on the deliverables this file applies them to* — `--html` / `--react`; a `--three` immersive page keeps the exemption stated in those sections — `prefers-reduced-motion`, no horizontal scroll, and the implementation mechanics of the three craft bullets below: OKLCH three-tier tokens, body text ≥16px / 65–75ch / line-height 1.5–1.75, no gray text on colored backgrounds, animate only transform/opacity, `transition` for anything interruptible, content never gated on a triggered animation, Grid/Flex with 4/8px tokens, semantic z-index, `min-h-100dvh`. These bind the final artifact regardless of what any reference does. "The reference does it that way" is not a defense. When a reference's treatment cannot meet a floor, keep the reference's look and fix the implementation (raise the contrast, add the focus ring, enlarge the tap target) — do not drop the floor, and do not drop the reference.
  - **Taste rules yield to a traced reference.** The anti-slop list, "no pure black / pure white", "accent ≤10% of area", "one primary CTA per screen", "UI animation <300ms / entrances from scale(0.95)" exist to stop *undecided* defaults. A value you can point at in a specific retrieved reference — a cream ground, a `#000` page, a 900ms hero entrance, two equal CTAs, a particular display face, a specific weight/size pairing — overrides the matching rule, and you follow the reference's exact pairings. A value you cannot trace back to a reference is a default leaking in: the rule applies in full. (Controls still obey the interruptibility floor above: a slow *entrance* is a taste call, a slow *hover/press response* is not.)
  - **Musepool's own rules win over a taste rule here when the two collide.** Its "color must come from references" decides the palette: background / accent / text derive from the references and semantic or status colors are derived from that palette (same temperature, saturation, lightness ladder) — never invented — and are then *implemented* through the OKLCH token tiers. Its "default traps" list (emoji / icon containers, nested cards, border + radius + accent strips, centered hero + two CTAs + three equal cards, formulaic display fonts) is **not** lifted by a reference: those are the anti-slop items the two lists share, and musepool's reading is that real references do not look like that — a retrieved item that does is a mis-read or poor match, so change the query rather than ship the trap. Its engineering hard rules bind as floors: a page containing Chinese carries an explicit CJK font stack (system CJK faces are legitimate there) and Chinese text never takes `font-style: italic`; the Inter/Roboto/system-default ban targets the unconsidered default face, not a face a reference actually uses.
  - **No downgrade, and no unverified effect.** Musepool's "implementation must not be downgraded" and Principle 3 here both bind: build the reference's technique for real *and* trigger it once in the browser with evidence. Shipping a simplified stand-in is a violation; so is shipping the full technique unlooked-at.
- **Color & typography**: OKLCH three-tier tokens (primitive→semantic→component); no pure black/pure white (use tinted off-black/off-white); accent ≤10% of area, no gray text on colored backgrounds; body text 65–75ch, ≥16px, line-height 1.5–1.75.
- **Interaction completeness**: every interactive element has hover/focus/active/disabled states + cursor-pointer + a visible :focus-visible; body contrast ≥4.5:1, large text/UI ≥3:1 (verify dark mode separately); hidden/dynamic UI (modal/dropdown/empty/loading/error/confirm) must all be implemented and keyboard-operable.
- **Motion discipline**: UI animation <300ms, ease-out preferred, animate only transform/opacity; entrances start from scale(0.95), exits are faster than entrances; use transition (not keyframes) for anything interruptible; content visibility must never be gated on triggered animation (visible by default); every animation degrades for prefers-reduced-motion.
- **Layout engineering**: Grid for 2D / Flex for 1D, spacing via 4/8px tokens with gap; semantic z-index (no 9999); one primary CTA per screen; full height via min-h-100dvh; no horizontal scrolling on mobile — test all of 375/768/1024/1440 breakpoints.
- Put game code in `src/game/` (engine, systems, content) when a game lives inside a React app, sharing project conventions with the rest of the code.
- Details in `website-design.md`.

## 3D effects on pages (making pages fancy with Three.js)

- **Technique ladder first**: DOM/CSS → 2.5D camera-facing planes → full 3D — pick the least complex option that preserves the requested depth; a full model with controls is overkill for decorative depth behind copy.
- **Content stays in the DOM**: headings, copy, CTA remain semantic HTML; decorative canvases get `aria-hidden` + `pointer-events:none`; interactive 3D targets need a named DOM/keyboard/touch alternative.
- **Never a black canvas**: ship a static poster/CSS composition that shows before the first GPU frame and on WebGL/shader/asset failure.
- **Scroll choreography**: one bounded progress value drives camera + shader + DOM (GSAP/ScrollTrigger when the motion has a designed timeline); branch for `prefers-reduced-motion`.
- Details in `website-design.md` ("3D effects on pages" section).

## PWA support

Scope: `--react` / `--template` deliverables. `--html` and `--three` deliverables are exempt by default; add PWA to those modes only when the user explicitly requests it.

For all in-scope tool-based and application-style websites, automatically implement basic PWA support even if the user does not explicitly request it. Include a web app manifest, app name and icons, standalone launch, theme color, installation support, and the necessary Service Worker configuration. Ensure mobile responsiveness. Generally skip PWA for content-only websites with little user interaction. Do not precache HTML or serve HTML entries/navigations cache-first; use network-first or network-only for `index.html` and navigation requests. Activate new Service Worker versions immediately (`skipWaiting` + `clientsClaim`, or `registerType: 'autoUpdate'` with vite-plugin-pwa): every saved version becomes the published site, so a cache-first Service Worker can keep serving the previous build after republication or rollback.

Create a consistent app icon system for every website. Reuse existing visual assets or generate icons with AI based on the website's visual style. Avoid drawing SVG icons directly in code. Icons should match the website's aesthetic, reflect its core purpose, and feature a clean, attractive design with a prominent, centered subject. Avoid fine details and unstyled single letters or Chinese characters. Maintain sufficient safe margins for different icon masks and cropping.

Once PWA support is complete, briefly inform the user that the website can be installed as a desktop or mobile app, and recommend adding it to their home screen. Mention this only once. Do not explain PWA details unless asked.

## Mobile web adaptation (`--html` / `--react` deliverables)

Scope: `--html` / `--react` deliverables. `--three` immersive pages (canvas-based) are exempt — they follow their own verification flow.

- **Responsive by default**: desktop-first design is fine, but it must not break at 375px mobile viewport. Rules R0–R6 (details in `mobile-adaptation.md`): R0 viewport meta required · R1 mobile-first + Tailwind breakpoints (default styles for mobile, `md:`/`lg:` layer desktop on top — never the reverse) · R2 no fixed pixel width >375px · R3 body text ≥14px (16px recommended), auxiliary ≥12px · R4 touch targets ≥44px · R5 hover-dependent features must also work on tap · R6 safe-area padding (only with full-screen background or bottom-fixed elements).
- **Device-priority routing (decide before coding)**: explicit mobile (phone App / mini-program / mobile / H5 / responsive) or implicit mobile scenarios (QR-code / food-delivery / check-in / photo-upload / location / social-share / push / vertical content) → **mobile-primary** (mobile-first writing; mobile experience is the main goal); admin dashboards / data boards / editors / office tools → **desktop-primary** (desktop-first writing, R0 + R2 floor still applies); no signal → **responsive default** (mobile-first writing). See `mobile-adaptation.md`.
- **Pre-delivery mobile check (route-conditional)**: ① *static* (grep, always) — built `index.html` contains `<meta name="viewport"`; no element fixed widths >375px (`w-[NNNpx]`, `width:`/`min-width: NNNpx` declarations; breakpoint-scoped rules — `@media (min-width:…)` queries and `md:`/`lg:`-prefixed utilities — and `max-w-`/`max-width` containers are legitimate, excluded); no `user-scalable=no` / `maximum-scale=1`. ② *visual* — **only when routing = mobile-primary or responsive-default**: the mobile-viewport screenshot shows no full-page horizontal scroll, no element off-screen, text readable, controls tappable. Desktop-primary → static grep is enough. Any red → attribute to a variable, fix, re-check — do not deliver with a red mobile check on the applicable route.

## Interaction integrity (`--html` / `--react` deliverables)

- **Every visible control must do something**: a button/link that renders but does nothing on click is a baseline defect (dead interaction), worse than not rendering it. Rules I0–I5 (details in `interaction-integrity.md`): I0 every button/a has a reachable action (JS handler / real href / form submit / details-summary / pure-CSS `:checked` toggle — at least one) · I1 no placeholder `href="#"` (exceptions: brand/home/back-to-top and anchors to existing ids) · I2 in-page anchors must point at an existing id · I3 hover is never the only entry (Mobile R5) · I4 social/external icons: real URL or don't render · I5 full-screen overlays must be closable (two of close button / Esc / backdrop click); non-modal full-screen covers that do not auto-dismiss within 1.5s are banned.
- **Implement or delete**: nav items, CTAs, cards, pagination, footer/social links rendered "for completeness" with no target are the top source of dead interactions — if you cannot name where it goes or what it does, do not render it.
- **Pre-delivery interaction check** (folds into Verification, no extra tooling): *static* (grep) — no `href="#"` outside brand/back-to-top/existing-id anchors; every `href="#id"` has a matching id; no `<button>` without handler evidence (`on*` attr / `submit|reset` in form / JS binding referencing its id|class|data-*).

## Verification (mandatory self-examination)

0. **Mobile check (route-conditional)**: viewport meta present in the built `index.html` (grep), no element fixed widths >375px in source (grep, `@media` breakpoints excluded) — **always**; the mobile-viewport screenshot (step 2) shows no full-page horizontal scroll / element off-screen / unreadable text / untappable controls — **only when routing = mobile-primary or responsive-default** (desktop-primary → static grep is enough). Do not deliver with a red mobile check on the applicable route. Checklist: `mobile-adaptation.md`.
1. **Interaction-integrity check**: no placeholder `href="#"` outside brand/back-to-top/existing-id anchors (grep); every `href="#id"` has a matching id; no handler-less buttons (grep + confirm binding) — dead controls are release blockers: fix or delete. Then the visual click check: in the real browser, click the main CTA and every nav item — each must produce an observable effect (navigation / scroll / modal / state change / form feedback); no effect → fix or delete. Checklist: `interaction-integrity.md`.
2. **Screenshot and look yourself**: load the page in a real browser (环境安装了 ego-browser Skill 时先读它并执行 ego-browser skill，优先使用其真实浏览器与登录态；未安装或确认不可用时，说明原因再用可用的 Playwright/Chromium 或宿主浏览器；不猜测 ego 的 Playwright 同名 API) — **zero console errors and zero 404s are a release gate**, record the console state before judging visuals; then one shot per key state (desktop viewport always; mobile viewport **only when routing = mobile-primary or responsive-default**; every page/route of a multi-page app; 3D-enhanced pages also get a full view + thumbnail of the scene) — open and look, **fix and re-shoot only if a defect is found** (no defect → no fix round, deliver).
   - **Frontend-only project**: serve the built `dist/` (`--react` / `--three`) or the project root (`--html`, which has no build step) with a static server and point the browser at that.
   - **Project with backend-building grafted on** (`--react` / template projects only — see Workflow): do **not** use a static server — the API only exists inside the Hono process. Verify with `npm run dev` and load `http://localhost:3000` (source + HMR, API attached); to check the production artifact, `npm run build && npm start` — that is the server that serves `dist/public`, and `dist/public` is what gets snapshotted, not `dist/`. Testing a backend project off a static server makes every tRPC call 404 and looks exactly like a broken backend — that is a verification-setup bug, not a server bug, so do not "fix" the backend in response to it.
3. **Triple-check the most frequent defects**: ① hidden/dynamic UI (modal/dropdown/empty/loading/error/confirm) all implemented and keyboard-operable; ② every form validates and shows feedback on submit; ③ any promised 3D/canvas effect actually renders — no dead or black canvas.
4. **Performance counts**: page weight, request count, render-blocking time, frame rate of any animated/3D section — from counters, not feelings.
5. **Finishing hygiene**: keep requested evidence; the deliverable matches its run instructions (goal/structure/run/techniques).
